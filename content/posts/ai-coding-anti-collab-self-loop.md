带领团队落地 AI Coding 后，真正的瓶颈很快会收敛到两个问题上：

1. 机器能不能自己拿到足够、可信的上下文？
2. 机器能不能自己判断「做完了没有」？

围绕这两个问题，有两条清晰的趋势正在浮现：**反协作**与**自循环**。

## 一、反协作：让机器自己去拿上下文

传统协作模式的核心成本，是上下文在人与人、人与机器之间反复传递。反协作的目标，就是尽量减少这种传递，让机器直接去系统里找到它需要的东西。

上下文大致可分为六类：

- **任务上下文**：Jira、项目看板、日常需求与进度
- **业务上下文**：领域术语、业务规则、合规要求、产品文档
- **决策上下文**：架构文档、ADR、架构原则、命名约定
- **代码上下文**：代码库本身
- **数据上下文**：数据库 schema 与数据
- **运行时上下文**：环境配置、日志、监控与告警

管理上下文的关键，不在于「把所有东西都塞进 prompt」，而在于**让机器能找到可信的上下文**。

这里有两层关键能力：

- **MCP（连接层）**：把外部系统统一封装成 AI 可调用的工具与资源，解决「能不能连上」的问题。
- **Skill（能力层）**：把流程、领域知识、验证步骤封装起来，让 Agent 知道「什么时候该拿什么、怎么用、怎么验证」。

未来研发的责任边界也会发生变化——人不再只对「任务」负责，而是对**具体结果**负责。这意味着工作天然会跨多业务域、多技术栈，上下文的可发现性因此变得更加重要。

## 二、自循环：任务循环 + 交付循环

自循环的目标是让机器自己完成「发现 → 执行 → 交付」的闭环。

它包含两个相互连接的循环：

**任务循环**
发现任务 → 探索上下文 → 规划 → 执行 → 验证 → 修复 → 完成

**交付循环**
构建 → 测试 → 预览 → 灰度 → 发布 → 监控 → 回滚 → 产出收据

两个循环靠「收据」（receipt）连接：任务循环产出变更，交付循环验证并发布，生产反馈再回流到任务循环。

重要原则是：模型可以提议「完成」，但不能自己宣布「完成」。通过或失败，只能由客观信号决定——测试结果、类型检查、lint、e2e、退出码等。

## 判断标准与人的角色

判断一个 AI Coding 系统是否真正落地，最终只看两点：

- 机器能不能自己拿到上下文？
- 机器能不能自己判断通过？

人的工作因此收窄为两件核心设计：

1. **设计工作台的可发现性**（让机器找得到可信上下文）
2. **设计流水线的可验证性**（让机器跑得通验证闭环）

## 总结

反协作，是把上下文放到机器能稳定找到的地方；  
自循环，是把验证做成机器能自主跑通的流程。

人负责设计这两件事。其余交给机器。
